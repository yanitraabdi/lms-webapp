# Browser Test Harness Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** a Playwright + axe suite that smoke-tests every live INVERTA page and drives one learner from sign-up to a verified certificate, locally and in CI.

**Spec:** `docs/superpowers/specs/2026-10-30-e2e-harness-design.md` (binding).

**Architecture:**
- An isolated compose project (`inverta-e2e`) runs the real stack.
- Playwright in `frontend/e2e/` talks to it at `http://localhost:3100`.
- Test-only helpers do two things the UI cannot: verify an email, and read answer keys. Both go through `docker compose exec postgres psql`.

**Tech stack:** `@playwright/test`, `@axe-core/playwright`, Chromium only, Node 22, Docker Compose v2.

## Global Constraints
- **Never touch the deployed stack or its config.** Every compose command in the harness uses `-p inverta-e2e --env-file e2e.env -f docker-compose.yml -f docker-compose.e2e.yml` (paths relative to the repo root). `--env-file` stops Compose from auto-loading the deployed root `.env`, which may set `EMAIL_PROVIDER=smtp` (real emails) or a different `POSTGRES_USER`. Ports: frontend 3100, API 8180, Postgres 5532.
- **Never read or print `.env`.** E2E config lives in `docker-compose.e2e.yml` with test-only values.
- **No production code changes** except:
  - fixes for axe `serious`/`critical` violations found in Task 2;
  - a `data-testid` where no role or text selector works.

  Each such change is listed in the task report.
- **Golden rules are asserted, never bypassed:**
  - no direct enrolment rows (GR-2);
  - no API call that returns answer keys (GR-11).
- **Selectors:** `getByRole` / `getByLabel` / `getByText` with the Indonesian UI strings.
- **Dormant routes are excluded:** `/catalog*`, `/modules/*`, `/pricing`, `/app/learn/*`, `/for-business`, `/style-guide`, `/feedback`.
- Tests run serially (`workers: 1`), because the stack is shared state.

**Interfaces (produced, used by Tasks 2–3):**
- `psql(sql: string): string`: runs SQL in the e2e Postgres and returns trimmed `-t -A` output.
- `verifyEmail(email: string): void`
- `correctAnswers(assessmentId: string): Record<string, number>`: question id → correct choice index.
- `api(path, { method?, token?, body? }): Promise<any>`: fetch against `BASE_URL/api`. Throws with status and body on a non-2xx response.
- `login(email, password): Promise<string>`: returns the access token.
- `ADMIN = { email, password }`: the values set in `docker-compose.e2e.yml`.
- `newLearner(): Promise<{ email, password, name, id }>`: registers a unique learner through the API, verifies the email, logs in once and marks the onboarding tour done (`POST /api/onboarding/tour` `{tourKey:"dashboard_first_run",status:"Completed"}`) so driver.js never overlays the dashboard.
- `gotoReady(page, path, ready: Locator)`: `page.goto`, then wait for `ready`. Every navigation in smoke and journey uses it, because refresh tokens rotate with reuse detection, and a `goto` that aborts an in-flight `/api/auth/refresh` revokes the whole token family.
- A Playwright fixture or `test.beforeEach` `addInitScript` that sets localStorage `academy_cookie_consent` (read `CookieConsent.tsx` for the value), so the fixed cookie banner never covers buttons or skews axe.
- `signIn(page, email, password)`: UI login, then waits for `/app/dashboard`.

### Task 2: Smoke + accessibility suite

**Files:**
- Create: `frontend/e2e/support/axe.ts`, `frontend/e2e/smoke.spec.ts`
- Modify: production files only to fix violations (listed in the report).

**Interfaces:** consumes `newLearner`, `signIn`, `ADMIN` from Task 1.

- [ ] **Step 1: `axe.ts`:**

```ts
import AxeBuilder from "@axe-core/playwright";
import { expect, type Page } from "@playwright/test";

/** Rules switched off on purpose. Every entry needs a reason; an empty list is the goal. */
export const DISABLED_RULES: Array<{ id: string; reason: string }> = [];

export async function expectNoSeriousA11y(page: Page) {
  const { violations } = await new AxeBuilder({ page })
    .withTags(["wcag2a", "wcag2aa", "wcag21a", "wcag21aa"])
    .disableRules(DISABLED_RULES.map((r) => r.id))
    .analyze();
  const bad = violations.filter((v) => v.impact === "serious" || v.impact === "critical");
  expect(bad.map((v) => `${v.id}: ${v.nodes.map((n) => n.target.join(" ")).join(", ")}`)).toEqual([]);
}
```

- [ ] **Step 2: `smoke.spec.ts`.** There are three groups. Each page gets the same `checkPage(page, path)`:
  - the response status is below 400;
  - the final URL path equals `path` (no redirect to /login or 404);
  - `page.locator("h1")` has count 1;
  - no `console` errors were collected during load;
  - `expectNoSeriousA11y`;
  - `document.documentElement.scrollWidth <= innerWidth`.

The groups:
  - **Public:** `/`, `/program/toefl-preparation`, `/about`, `/how-it-works`, `/help`, `/contact`, `/login`, `/register`, `/forgot-password`, `/verify/UNKNOWN-CODE` (the invalid state must render). Add `/legal/<key>` for every key of `DOCS` in `app/(marketing)/legal/[doc]/page.tsx`, and every other non-dormant route under `app/(marketing)`.
  - **Learner** (`test.describe` with `beforeAll` → `newLearner`, and `beforeEach` → `signIn`): `/app/dashboard`, `/app/certificates`, `/app/account`, `/app/notifications`.
  - **Admin** (`signIn` with `ADMIN`): every page under `app/admin` that is not a dormant route (curriculum/modules/pricing are excluded). List the directory to build the array. Pages with `[id]` segments are skipped.

Pages that legitimately redirect (`/` → `/program/toefl-preparation`) get their expected final path in the table.

### Task 3: Learner journey (enrol → certificate)

**Files:**
- Create: `frontend/e2e/journey.spec.ts`

**Interfaces:** consumes all Task 1 helpers.

One `test.describe.serial` with one learner. Steps are `test.step`s inside a single `test` (timeout 5 min). Read the components named below for the exact strings before writing selectors.

- [ ] **Step 1: Enrol through the real webhook path (GR-2).**
  1. `newLearner` → `signIn`.
  2. Go to `/program/toefl-preparation` and click "Daftar sekarang" (`EnrollCta.tsx`).
  3. Expect the URL `/checkout/dev-pay`.
  4. Assert that `api("/programs/...")` or the dashboard still shows the learner as not enrolled at this point. Use what the dashboard renders for a non-enrolled learner, and read `app/app/dashboard` to pick the signal.
  5. Click "Bayar sekarang (berhasil)" → expect `/checkout/success`.
  6. Go to `/app/dashboard` → the TOC shows session 1 as current (`aria-current="step"`).

- [ ] **Step 2: Linear lock (GR-8).** Read the session ids with `psql` (`program_sessions` joined to `programs` by slug, ordered by `order_index`). Opening `/app/session/<session 2 id>` must not show session 2's content; assert the locked state SessionView renders. `POST /api/sessions/{session2}/parts/{partId}/playback` must return exactly 403.

- [ ] **Step 3: The gating test truly gates.**
  1. PUT progress `percent: 100` on session 1's lesson part (`SessionEndpoints.cs:43`; get part ids via `psql` on `session_parts`).
  2. Reload the dashboard: session 1 is still current, not done.
  3. Fetch the learner-facing assessment (`GET /api/sessions/{sid}/parts/{partId}/assessment`). Assert `JSON.stringify(body)` contains no `"correct"` key (GR-11). Step 7 repeats this check on `/api/sessions/{finalId}/parts/{partId}/assessment` and `/api/attempts/{id}/state`.

- [ ] **Step 4: Pass session 1's test in the UI.**
  1. Open session 1 and click "Mulai tes" (`GatingTest.tsx`).
  2. For every question, pick the choice whose index is `correctAnswers(assessmentId)[qid]`.
  3. Each radio has `name="q-{questionId}"` (`GatingTest.tsx`). Select by `input[name="q-${qid}"]` and its nth choice; no test ids needed.
  4. Submit. Expect the pass state, and the dashboard shows session 1 ✓ and session 2 current.

- [ ] **Step 5: Sessions 2–6 via the API.** Per session:
  1. PUT progress 100 on the lesson part.
  2. `POST /api/assessments/{id}/attempts`.
  3. `POST /api/attempts/{id}/submit` with the DB answer key.

  Read `SessionEndpoints.cs` for the `answers` body shape. Expect the dashboard to show 6 done and Live current.

- [ ] **Step 6: Live session via the admin API.** `login(ADMIN)`, then `POST /api/admin/sessions/{liveId}/attendance` with `{ userIds: [learnerId], attended: true }`. Get `learnerId` via `psql` on `users` by email. Expect the final assessment row to be current.

- [ ] **Step 7: Final assessment in the UI.**
  1. Open session 8 and click the "Mulai tes akhir" link. Expect `/app/assessment/<sessionId>`. Then click `getByRole("button", { name: "Mulai tes", exact: true })` and expect `/app/exam/<attemptId>`.
  2. In each of the 3 sections, answer the first 3 questions with choice 0 (radios named `q-{id}`, `Sitting.tsx`), then click "Bagian berikutnya" (and "Selesaikan tes" on the last). Confirm any dialog.
  3. Do not open another page or tab during the sitting.
  4. Expect the result view: a numeric score, and the text "bukan skor TOEFL resmi" (GR-14).

- [ ] **Step 8: Certificate and verify page.**
  1. Open `/app/certificates`. One certificate shows; read its verification code from the page.
  2. Open `/verify/<code>`: it shows the valid state, the learner's name and "bukan skor TOEFL resmi".
  3. Open `/verify/NOPE-0000`: it shows the invalid state.

- [ ] **Step 9: Run it twice in a row** (`npx playwright test journey --repeat-each=2`). Each run creates its own learner, so both must pass.

- [ ] **Step 10: Commit:** `test(e2e): learner journey from enrolment to verified certificate`

### Task 4: CI job and docs

**Files:**
- Modify: `.github/workflows/ci.yml` (new `e2e` job)

- [ ] **Step 1: Add the job:**

```yaml
  e2e:
    runs-on: ubuntu-latest
    needs: [backend, frontend]
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 22
      - run: npm ci --prefix frontend
      - run: npx --prefix frontend playwright install --with-deps chromium
      - run: npm --prefix frontend run e2e:up
      - run: npm --prefix frontend run e2e
        env:
          CI: "true"
      - if: failure()
        run: docker compose -p inverta-e2e --env-file e2e.env -f docker-compose.yml -f docker-compose.e2e.yml logs api frontend --tail 200
      - if: failure()
        uses: actions/upload-artifact@v4
        with:
          name: playwright-report
          path: frontend/playwright-report
          retention-days: 7
```

Note: `npm --prefix frontend run e2e` runs with cwd `frontend/`, so `../docker-compose.yml` resolves. Check that `npx --prefix` resolves `playwright`; otherwise use `working-directory: frontend` on those steps.

- [ ] **Step 2: Validate the workflow syntax locally** with `npx --yes action-validator .github/workflows/ci.yml`, or `actionlint` if installed. Check it parses; it does not need to run.
